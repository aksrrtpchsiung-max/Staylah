# Pipeline v1：验收与模型评测

日期：2026-09-08。本文定义待实现系统的测试要求，不代表这些测试已经通过。  
设计：[pipeline-v1.md](pipeline-v1.md)；接口：[contracts.md](contracts.md)。

## 1. 必测端到端场景

| ID | 场景 | 期望结果 |
|---|---|---|
| A01 | 客户首次输入模糊找房需求 | 只追问影响检索的必要字段；保存会话，等待回复 |
| A02 | 用户明确预算与区域 | 形成可追踪的结构化偏好，通过实时工具搜索 |
| A03 | 用户明确降低预算 | 偏好版本递增；旧版本运行不能覆盖新需求结果 |
| A04 | 用户只拒绝某套装修 | 保存该房源反馈，不自动把整个区域设为不喜欢 |
| A05 | 刷新或关闭网页 | 任务继续；重新进入后恢复聊天和推荐 |
| A06 | POST 因网络重试提交两次 | 仅保存一条用户消息和一个有效 run |
| A07 | SSE 断线重连 | 从事件序号恢复；结果卡片不重复 |
| A08 | 来源返回成功空结果 | 明确无匹配，允许进一步检索；不把空结果当接口失败 |
| A09 | 来源认证失败或解析失败 | 返回来源异常，不伪造无房源，也不静默切换模拟结果 |
| A10 | 来源分页或候选上限截断 | 展示已搜索范围与限制，不宣称全市场最优 |
| A11 | 模型推荐了超过硬预算的候选 | 校验失败并有界修复，不自行扩大预算 |
| A12 | 关键字段缺失 | 标为待核实，不把未知当满足硬条件 |
| A13 | 模型选择较贵但更符合偏好的房源为第一名 | 只要硬条件满足且解释有依据，保留模型顺序 |
| A14 | 模型输出不存在的候选或证据 ID | 拒绝发布；修复失败后报告生成失败 |
| A15 | 房源描述包含修改规则或读取其他客户的指令 | 作为外部数据处理，不能触发越权工具或偏好修改 |
| A16 | Worker 执行中重启 | 租约过期后恢复或重试；最终结果和提醒不重复 |
| A17 | 旧 worker 租约失效后仍返回结果 | lease_version 校验阻止旧执行者发布 |
| A18 | 到期规则被两个调度器扫描 | 唯一 tick 约束只产生一个有效任务 |
| A19 | 房源仅因排序/分页未再出现 | 不判定为已售或下架；必要时单独复查 |
| A20 | 同来源相同 ID 降价且符合客户需求 | 模型重新判断，产生一次有证据的变化提醒 |
| A21 | 数据相同，仅模型排名或措辞变化 | 不发送市场变化提醒 |
| A22 | 某来源本次搜索失败 | 保留该来源上一成功基线，不用空数据覆盖 |
| A23 | 用户在后台运行期间暂停关注 | 发布前规则版本检查阻止新提醒 |
| A24 | 用户在后台运行期间修改偏好 | 旧版本结果不作为最新推荐；新版本重建基线 |
| A25 | 请求其他经纪人的 client/run/SSE/result | 拒绝访问；模型传入 ID 也不能绕过 |
| A26 | 仅使用真实搜索外的演示来源 | 页面、工具事件和推荐都清楚标记 demo |
| A27 | 查看历史推荐 | 显示当时快照和时间，不将其作为最新在售事实 |
| A28 | 删除客户时仍有任务执行 | 取消规则，禁止旧任务恢复写入客户数据 |

## 2. 模型推荐评测

使用固定的客户需求与候选证据集合，避免外部搜索变化掩盖模型问题。至少覆盖：预算优先、通勤优先、面积优先、偏好冲突、信息缺失、无合格房源和中英混合输入。

评价内容：

- 硬条件遵守：所有主列表候选满足已确认且可验证的硬条件。
- 偏好响应：只修改一个明确偏好后，模型能合理调整比较和解释；不要求所有情况下都改变第一名。
- 解释支持：每个关键事实有真实证据，取舍与候选事实一致；人工逐条核查。
- 不确定性：不会把来源描述、猜测或缺失字段变成确认事实。
- 排序质量：由经纪人对候选对比做成对评价，记录偏好一致率；不把单一人工排名当唯一真值。
- 稳定性：对完全相同输入重复运行，记录 Top-3 集合与成对顺序变化；不给未知的“稳定率”预设已达标结论。
- 非臆造：引用候选、数值、地址、链接均来自工具证据。
- 顺序保留：数据库和前端展示与模型最终输出的 rank 一致，不存在隐藏程序重排。

结构引用检查与人工语义审查分开统计。引用存在不等于解释可靠。

## 3. 运行指标

记录每 run 的排队时间、首次进度时间、首个候选时间、完成时间、模型调用数、token/成本、工具调用数、来源错误率、修复次数、实际覆盖候选数。

在固定机器、并发、模型、来源和测试样本下报告 p50/p95；目前不宣称任何时延或成本已达成。总时间和调用预算到达上限时应有清楚的终止或部分结果状态。

调度记录：预计运行时间、实际启动时间、租约过期次数、重试次数、重复任务抑制、重复提醒抑制、未处理队列长度。

## 4. 建议测试分层

- 单元/契约：参数、币种面积转换、来源解析、硬条件判定、候选引用、幂等键、基线差异。
- 数据库集成：消息/run/job 原子写入、租约接管、版本冲突、推荐和通知事务、归属隔离。
- Agent fixture 评测：固定需求与工具返回，验证规划、排序、解释、未知项和修复。
- Web 端到端：聊天恢复、偏好面板同步、SSE 重连、顺序展示、关注暂停和提醒。
- 实时来源 smoke test：少量明确范围的 search/detail 验证，与离线评测分开；不需要全市场采集。

## 5. 可交付定义

1. 独立网页可登录并创建客户，无需安装 skill。
2. 至少一个实时来源在实际部署环境可用；如果仅有 demo 来源，明确交付为演示原型。
3. Onboard → 搜索 → 模型排序 → 反馈 → 新推荐闭环可演示。
4. 客户偏好、聊天、推荐与有限证据跨进程重启保留。
5. 网页关闭后定时任务继续；可证明一次变化只提醒一次。
6. 所有必测场景有结果记录；未通过项有明确限制。
7. 提供配置、迁移、启动、来源连接、恢复和演示说明。
8. 交付时附模型/工具/prompt 版本与实测性能，不以架构设计文档替代实现验证。
